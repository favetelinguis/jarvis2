# Jarvis2

An Elixir control plane for Herdr, under development according to [PLAN.md](PLAN.md).

## Current scope

The app runs a loopback HTTP server with `/healthz`, `/status`, an authenticated dashboard, and JSON hooks at `/hook/:kind/:id`. It subscribes to Herdr events, refreshes an in-memory session mirror, and keeps a bounded event history. Implemented actions include attention routing, sidebar tokens, optional pane hygiene, focus mode, a developer layout, and a dashboard popup. Context and issue-link actions log a restricted view; the HexDocs link action can open a popup, and several other actions remain log-only. Ctrl-click dispatch and worktree hooks remain unverified.

`jarvis2://layout` includes the latest net layout diff: membership, focus, geometry, split ratios, agent state, and worktree-change counts. Diffs are limited to 64 changes, flag truncation, and report `resynced` after a subscription gap or `unavailable` for invalid or oversized projections. Projection limits are 2,048 entities per list and 4,096 nested geometry/split entries or worktrees. Diffs compare sampled fresh snapshots, not every intermediate event; sequences reset on restart. Check the resource's `stale` flag before relying on its latest diff. Diff entries omit label values and checkout paths, although the full layout resource still contains them.

The authenticated streamable HTTP MCP endpoint provides identity, logging, blackboard, agent and layout discovery, worktrees, status reporting, notifications, guarded prompts, agent spawning, command execution, event waits, and `apply_layout`. `run_mix` executes an allow-listed Mix task; `ask_human` returns the first choice in dry mode and can open an opt-in human picker. Several scenarios are still planned. Browser-origin requests to `/mcp` and `/dashboard` are rejected; these endpoints are intended for local clients.

From the repository root, run `mix deps.get`, then start with `iex -S mix` (or `mix run --no-halt`). The default port is `4747`; set `JARVIS2_PORT` to override it. A bearer token is created at `$HERDR_PLUGIN_STATE_DIR/token`, or at `~/.local/state/herdr/plugins/favetelinguis.jarvis2/token` when that variable is unset. Its file mode is restricted to `0600`.

For example, while the server is running:

```sh
curl http://127.0.0.1:4747/healthz
curl -H "Authorization: Bearer $(< ~/.local/state/herdr/plugins/favetelinguis.jarvis2/token)" \
  -H 'Content-Type: application/json' -d '{}' \
  http://127.0.0.1:4747/hook/action/probe
```

Herdr writes default to dry-run. Live requests require both `JARVIS2_LIVE=1` and a scenario in `:live_scenarios` in `config/config.exs`. The focus view, developer layout, and dashboard use `:focus_mode`, `:declarative_layout`, and `:dashboard` respectively. The layout creates a **new** tab with three labelled shells; it never replaces an existing tab or starts an agent. It exports that tab and, if the returned layout is unchanged, adjusts its root split from 0.55 to 0.65. The MCP result reports whether the demonstration completed, was skipped, or is unconfirmed. Export and resize are not atomic, so another client can still change the new tab between them; inspect state before retrying an uncertain creation or resize. The dashboard shows bounded event and MCP journal summaries. Live `prompt_agent` requires `:agent_prompt`; `spawn_agent` and `run_command` require `:agent_spawn` and `:run_command` respectively. The generic mutation interface still refuses raw agent starts and pane/agent input. The explicit `start-server` plugin action opens a server pane even in dry-run mode, so it can bootstrap the app. Linking the plugin changes global Herdr registration; ask before running `herdr plugin link`.

`:sidebar_tokens` enables `report_status`'s `$jarvis` pane token, the `$agent_state` pane token on agent transitions, and the `$last_tool` Space token on MCP calls. Tokens expire after 60 seconds. Reports and queued updates require a fresh mirror; updates are coalesced and best-effort. `:pane_hygiene` independently enables renaming detected agent panes to `kind` or `kind: summary` and, when known, their tab to the linked worktree branch. It can overwrite manual labels. Status summaries appear in Herdr when live, so do not include secrets. See `examples/herdr-config.snippet.toml` for sidebar rows.

Live focus and token state is saved best-effort to `restore.json` in the state directory (mode `0600`). It can include status summaries. After an app restart, Jarvis2 restores only when the socket path, device, inode, and change time still match and, for tokens, the pane, terminal, and agent identity still match; the corresponding live scenario must still be enabled. This fingerprint is a best-effort identity check, not authentication. Remaining token TTL is not extended. Expired values are removed while the app runs or when that session's state is next loaded; if the app is stopped or the Herdr session changes, the file can retain them until replaced or removed. Do not use a shared state directory for concurrent app instances.

`prompt_agent` requires a fresh mirror and a detected caller, targets only a ready agent in the same workspace, refuses self-prompts, and limits each caller to four attempts per minute. A process-local, bounded graph rejects cycles in prompts routed through Jarvis2 until the app restarts; it deliberately disallows even later reciprocal handoffs. Prompts to a target are serialized with a cooldown, and uncertain failures are not retried. `wait=true` has a 60-second Herdr deadline. These are PoC safeguards, not a security boundary: pane headers are advisory, graph/rate state is not shared across app instances or retained on restart, and Herdr does not provide an atomic expected-occupant precondition. A target may change between snapshot validation and submission. A disposable Herdr session verified prompting a real Pi agent using a local mock model.

`:docs_link` enables the HexDocs link popup. It requires `w3m` on the plugin's PATH; without it the popup shows an installation message. Only HTTPS URLs on `hexdocs.pm` are accepted initially, though normal browser navigation and redirects are not restricted.

`:human_picker` enables `ask_human` to open a popup in the active Herdr client. It accepts a choice or free-text answer and times out if unanswered; closing it without answering also waits until the deadline. Requests are bounded and expire, answers are single-use, and the question and answer are not logged. The popup reads the local bearer-token file, and a client with that token and request ID can answer; this is not multi-user authentication. The question is visible in the popup, so do not include secrets. The `send-to-agent` action uses two pickers and the guarded prompt path; both `:human_picker` and `:agent_prompt` must be enabled.

`spawn_agent` and `run_command` create a sibling pane in the caller's current directory; they require a fresh recognized caller, recheck the created terminal and its exclusive foreground shell, limit each caller to four attempts per minute, and serialize operations per caller. A partial or uncertain result has a 60-second cooldown; inspect the workspace before retrying. These checks are process-local and cannot prevent races with other Herdr clients. Agent startup is asynchronous at the socket API, so readiness is checked separately. Optional spawn prompts also require `:agent_prompt`. `run_command` sends a single shell line to the new pane; it is **not sandboxed**, and an output match can match the echoed command rather than completed output. Progress notifications require a connected MCP event stream. Neither command nor prompt text is logged by the execution guard, but both are visible in the destination terminal.

`run_mix` is limited to the project directory where the server started and one task at a time. It requires GNU `timeout` and can execute that project's code even in dry-run mode; it is **not a sandbox**. With `:custom_worker` enabled, it also reports a `jarvis2-mix` agent on the server's own pane, from working to idle on success or blocked on failure. Herdr records idle as a completion. Reporting is best-effort: it checks that the server VM is in the pane's foreground process group and does not overwrite a different detected agent, but checks and writes cannot be atomic. A failed or uncertain report is not retried, and the Mix job still runs; inspect the server pane if its displayed status is stale. The agent persists in that pane until released or the pane closes. `elixir_eval` is off unless `JARVIS2_ALLOW_EVAL=1` is set at startup, and remains hidden in the supplied Pi configuration. When enabled it executes arbitrary code in the server VM: its timeout does not isolate side effects or child processes.

Human-invoked workflow actions (all dry-run by default; each launches agents, which can edit files and call tools):

- **`issue-link` / `new-task`** (`:worktree_task` plus `:agent_spawn`; `new-task` also needs `:human_picker`): create a linked Git worktree workspace `task/<slug>` from the focused workspace and start a `pi` agent there (`:task_agent_kind`, default `pi`). A GitHub issue or pull-request URL, or the typed task text, becomes the agent's launch argument, so no running agent is prompted. The source must be inside a Git repository. By default Herdr chooses the checkout path; set `:worktree_root` to place checkouts under `<root>/<repo>/<slug>`. Each workspace is limited to four attempts per minute and cools down for a minute after a failure. A worktree and its branch persist until you remove them.
- **`review-diff`** (`:review_fanout` plus `:agent_spawn`): starts up to three reviewer agents (`:review_focuses`, default `["bugs", "tests"]`) in sibling panes, each told to review `git diff HEAD` without modifying files. That instruction is not enforced. Their final output (last 2,000 characters each) is stored on the blackboard as `review:latest`, replacing the previous result. Waiting is best-effort: if Herdr never reports a reviewer as working, its status is `idle_unobserved` and the output may predate its answer.
- **Test loop** (`:test_loop` plus `:run_command` and `:agent_prompt`): when an agent in a Mix project under `:test_loop_roots` (default the server's project directory) finishes a turn, runs `mix test` in a sibling pane. On failure it prompts that agent with a sanitized output tail, up to three consecutive failures per pane and at least 20 seconds apart. This runs project code, is not sandboxed, and the output tail may contain secrets printed by tests. The pane read can include the echoed command and shell prompt.

Herdr serves one request per connection and resets concurrent ones that share it, so Jarvis2 opens a connection per request.

The supplied `.pi/mcp.json` applies only after Pi project trust is granted. It assumes the default port and token path; adjust it if `JARVIS2_PORT` or `HERDR_PLUGIN_STATE_DIR` differs. Pi discovery and `whoami`/`log` calls from an isolated Herdr pane were tested with temporary Pi configuration and one-run trust approval; your project trust has not been changed. Agent identity is advisory and becomes `unknown` when the mirror is stale or the pane cannot be resolved.

From the repository root, run `mix test`, `mix format --check-formatted`, and `mix credo` to check the project. Tests live under `apps/*/test`, with end-to-end tests in `apps/jarvis_web/test`. Credo currently reports existing code-quality findings.
